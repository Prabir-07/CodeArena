# Database Overview

The Problem Service uses **PostgreSQL** as its database and **Prisma** as its ORM, in its own database (`problems_db`), entirely separate from the User Service's.

PostgreSQL suits the data because it is genuinely relational: every `Example` and `TestCase` belongs to exactly one `Problem`, problems and tags form a many-to-many relationship, and replacing a problem's test-case set must be atomic. The schema relies on real foreign keys, a composite primary key and unique constraints to enforce integrity at the database level rather than only in application code.

---

# Entity relationship overview

```
Problem
 ├──< Example        (1:N, public content)
 ├──< TestCase       (1:N, hidden content)
 └──< ProblemTag >── Tag   (N:M through an explicit join table)
```

- **Problem → Example** — one-to-many. Public worked examples shown on the problem statement.
- **Problem → TestCase** — one-to-many. Hidden test cases used for judging.
- **Problem ↔ Tag** — many-to-many, through the explicit `ProblemTag` join table. A problem has any number of tags; a tag applies to any number of problems.

## Why Example and TestCase are separate tables

This separation is the core privacy boundary of the service, and it is structural rather than a matter of convention.

- `Example` is **public**: input, output and an optional explanation, rendered on the problem page.
- `TestCase` is **hidden**: the input/expected-output pairs a judge grades against.

They are never the same table and never the same rows, even when their content happens to overlap. No public repository `select` references `TestCase` at all, and public responses are additionally built by sanitizers that name every field explicitly — so a `TestCase` row cannot reach a public response even if a repository projection later changes. Test cases are reachable only through the admin authoring endpoints and the shared-secret internal endpoint.

## Why ProblemTag is an explicit join table

Rather than an implicit Prisma many-to-many or a `String[]` column on `Problem`, `ProblemTag` is modelled explicitly. This gives `GET /tags` a real grouped join for its per-tag published counts instead of unnesting an array column, and normalises tag names once rather than duplicating free text on every problem.

## No relational dependency on the User Service

This schema contains **no user table, no user foreign key, and no cross-database relation**. The Problem Service holds nothing about accounts. Where a user matters, it is referenced by the id carried in the JWT — there is no foreign key into the User Service's database, and neither schema needs to change when the other does.

## Cascade behaviour

All three child relationships are declared `onDelete: Cascade` (with `onUpdate: Cascade` in the generated SQL). Deleting a `Problem` removes its `ProblemTag`, `Example` and `TestCase` rows automatically, enforced by PostgreSQL rather than by application code. `ProblemTag` also cascades from `Tag`, so deleting a tag removes its associations.

Deleting a problem does **not** delete `Tag` rows — a tag may be shared with other problems, and an orphaned tag is retained (see [Known limitations](README.md#known-limitations-and-future-work)).

# Difficulty enum

```prisma
enum Difficulty {
  EASY
  MEDIUM
  HARD
}
```

Stored uppercase, matching the `Role` enum convention in the User Service. The public API translates these to `"Easy"` / `"Medium"` / `"Hard"`; the admin API returns the raw enum value. See [API.md](API.md#a-note-on-response-shapes).

# Problem table

Maps to the `problems` table.

| Column | Purpose | Type | Nullable | Default | Constraints |
|---|---|---|---|---|---|
| `id` | Primary key. | `String` (`text`) | No | Client-side UUID generated by Prisma. | Primary key. |
| `slug` | Public, URL-safe identifier. The only identifier the public API exposes. | `String` (`text`) | No | None | **Unique.** |
| `title` | Display title. | `String` (`text`) | No | None | None |
| `difficulty` | Problem difficulty. | `Difficulty` enum | No | None | Constrained to the enum by PostgreSQL. |
| `summary` | One-line description for the catalogue listing. | `String` (`text`) | No | None | None |
| `description` | Full problem statement. | `String` (`text`) | No | None | None |
| `constraints` | Constraint lines shown beneath the statement. | `String[]` (`text[]`) | No | `[]` | Native PostgreSQL text array. |
| `functionSignature` | Canonical language-agnostic signature: `{ name, params: [{ name, type }], returnType }`. | `Json` (`jsonb`) | No | None | Shape enforced by application-layer validation, not by the database. |
| `isPublished` | Whether the problem appears in the public catalogue. | `Boolean` | No | `false` | New problems are drafts. |
| `createdAt` | Row creation timestamp. Also the public listing's sort key (newest first). | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP` | None |
| `updatedAt` | Last-modified timestamp. | `DateTime` (`timestamp(3)`) | No | Maintained by Prisma (`@updatedAt`). | None |

**Why `functionSignature` is JSON rather than normalised.** It is always read and written whole alongside its problem and is never queried into independently, so a normalised child table would add join cost for no benefit. The trade-off is explicit: PostgreSQL does not enforce its shape, so a Zod schema validates it on every write.

**Why `isPublished` exists.** Authoring is a multi-step process, so a problem must be creatable and editable before it is publicly visible. Every public read is scoped to `isPublished: true`, which is what makes a draft indistinguishable from a nonexistent problem.

# Tag table

Maps to the `tags` table.

| Column | Purpose | Type | Nullable | Default | Constraints |
|---|---|---|---|---|---|
| `id` | Primary key. | `String` (`text`) | No | Client-side UUID. | Primary key. |
| `name` | Tag name as displayed, e.g. `Hash Table`. | `String` (`text`) | No | None | **Unique.** |

The unique constraint on `name` is what makes find-or-create safe: authoring uses `connectOrCreate`, so a tag is reused when it exists and created when it does not, without risking duplicates under concurrent writes.

# ProblemTag table

Maps to the `problem_tags` table. The explicit join between `Problem` and `Tag`.

| Column | Type | Nullable | Constraints |
|---|---|---|---|
| `problemId` | `String` (`text`) | No | Foreign key → `problems.id`, `ON DELETE CASCADE ON UPDATE CASCADE`. |
| `tagId` | `String` (`text`) | No | Foreign key → `tags.id`, `ON DELETE CASCADE ON UPDATE CASCADE`. |

**Primary key:** composite, `(problemId, tagId)`. This is what makes the same tag impossible to attach to the same problem twice — the constraint is structural, not an application check.

There is no surrogate `id` column and no timestamps: the row's existence *is* the association.

---

# Example table

Maps to the `examples` table. **Public content.**

| Column | Purpose | Type | Nullable | Default | Constraints |
|---|---|---|---|---|---|
| `id` | Primary key. | `String` (`text`) | No | Client-side UUID. | Primary key. |
| `problemId` | Owning problem. | `String` (`text`) | No | None | Foreign key → `problems.id`, `ON DELETE CASCADE`. Indexed. |
| `input` | Example input, as displayed. | `String` (`text`) | No | None | None |
| `output` | Example output, as displayed. | `String` (`text`) | No | None | None |
| `explanation` | Optional prose explaining the example. | `String?` (`text`) | Yes | None | The only nullable column in the schema. |
| `order` | Display position within its problem. | `Int` (`integer`) | No | None | Assigned from array position on write; never client-supplied. |
| `createdAt` | Row creation timestamp. | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP` | None |

`order` is not exposed publicly — the public API returns examples already sorted, as an ordered array.

# TestCase table

Maps to the `test_cases` table. **Hidden content — never returned by any public endpoint.**

| Column | Purpose | Type | Nullable | Default | Constraints |
|---|---|---|---|---|---|
| `id` | Primary key. | `String` (`text`) | No | Client-side UUID. | Primary key. |
| `problemId` | Owning problem. | `String` (`text`) | No | None | Foreign key → `problems.id`, `ON DELETE CASCADE`. Indexed. |
| `input` | Input fed to the submitted program. | `String` (`text`) | No | None | Stored byte-exact — never trimmed. |
| `expectedOutput` | Output the program must produce. | `String` (`text`) | No | None | Stored byte-exact — never trimmed. |
| `order` | Position within the problem's test-case set. | `Int` (`integer`) | No | None | Assigned from array position on write; never client-supplied. |
| `createdAt` | Row creation timestamp. | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP` | None |
| `updatedAt` | Last-modified timestamp. | `DateTime` (`timestamp(3)`) | No | Maintained by Prisma (`@updatedAt`). | None |

**Why whitespace is preserved.** A judge compares program output byte for byte. A trailing newline in `expectedOutput`, or leading indentation in `input`, is significant data — so unlike the display-oriented `Example`, these strings are never trimmed by validation.

**Replacement semantics.** The API replaces a problem's whole test-case set rather than editing individual rows, inside a single transaction. Row ids are therefore not stable across a replacement, which is why the judge-facing response omits `id` entirely.

**Seeded state.** The database ships with **zero** test-case rows. The source dataset contained none, and fabricating hidden test data would give a judge meaningless input, so seeded problems legitimately have none until an admin authors them.

# Indexes

| Table | Index | Type | Reason |
|---|---|---|---|
| `problems` | `problems_pkey` on `id` | Primary key (btree) | Row lookup by id — admin reads, and the existence check behind the test-case endpoints. |
| `problems` | `problems_slug_key` on `slug` | Unique (btree) | Enforces slug uniqueness and makes public lookup by slug an indexed hit. |
| `tags` | `tags_pkey` on `id` | Primary key (btree) | Row lookup by id. |
| `tags` | `tags_name_key` on `name` | Unique (btree) | Enforces tag uniqueness and backs find-or-create during authoring. |
| `problem_tags` | `problem_tags_pkey` on `(problemId, tagId)` | Composite primary key (btree) | Prevents duplicate associations; also serves lookups by `problemId`. |
| `problem_tags` | `problem_tags_tagId_idx` on `tagId` | Non-unique (btree) | Makes "problems carrying this tag" and the per-tag published counts indexed lookups rather than table scans. |
| `examples` | `examples_pkey` on `id` | Primary key (btree) | Row lookup by id. |
| `examples` | `examples_problemId_idx` on `problemId` | Non-unique (btree) | Makes "all examples for this problem" — every problem-detail read — an indexed lookup. |
| `test_cases` | `test_cases_pkey` on `id` | Primary key (btree) | Row lookup by id. |
| `test_cases` | `test_cases_problemId_idx` on `problemId` | Non-unique (btree) | Backs both reads and the delete half of a set replacement. |

There is deliberately **no** index on `problems.title`, despite the public listing's case-insensitive substring search. At the current catalogue size a sequential scan is not a bottleneck; a trigram or full-text index is the natural change if search ever becomes hot.

There is no separate index on `problem_tags.problemId`, because the composite primary key already covers it as its leading column.

# Constraints

**Unique**

- `problems.slug` — one problem per public identifier.
- `tags.name` — one row per tag name.

**Composite primary key**

- `problem_tags (problemId, tagId)` — a tag can be attached to a problem at most once.

**Foreign keys** (all `ON DELETE CASCADE ON UPDATE CASCADE`)

- `problem_tags.problemId → problems.id`
- `problem_tags.tagId → tags.id`
- `examples.problemId → problems.id`
- `test_cases.problemId → problems.id`

There are no foreign keys leaving this database.

# Prisma design

**Generated client output.** `schema.prisma` sets a service-local generator output:

```prisma
generator client {
  provider = "prisma-client-js"
  output   = "../src/generated/prisma-client"
}
```

This repository is an npm workspace containing more than one Prisma schema. With Prisma's default output, both services generate into the same hoisted `node_modules/@prisma/client`, and whichever service ran `prisma generate` last would silently overwrite the other's client — breaking its queries at runtime. The service-local path removes that shared location entirely, which is why `src/config/prisma.js` and `prisma/seed.js` import from `../generated/prisma-client` rather than `@prisma/client`, and why `@prisma/client` is not a dependency of this service.

The generated directory is gitignored, so `prisma generate` must run after a fresh clone.

**Migrations.** `prisma/migrations/` holds the ordered, version-controlled schema history, with its own `migration_lock.toml` independent of the User Service's. Any environment reaches the current schema by replaying the same migrations.

**Transactions.** `prisma.$transaction` wraps the test-case replacement, so the existence check, the delete and the insert either all succeed or all roll back — a problem never ends up with a partially-replaced test-case set.

**Repository pattern.** Only `repositories/` calls `prisma.<model>.*`. Each function accepts an optional Prisma client argument, defaulting to the shared singleton, which is how one logical operation spanning several repositories runs inside a single transaction by passing the transaction-scoped client through.

**Explicit selects.** Repository reads use explicit `select` objects rather than returning whole rows. The public and judge-facing projections deliberately omit `TestCase` and internal columns, and the sanitizers in `utils/` rebuild responses field by field as a second layer of defence.

# Development and test databases

Both are the same PostgreSQL instance (`codearena-postgres-problems`, host port 5433, database `problems_db`), separated by schema:

| Schema | Used by | Contents |
|---|---|---|
| `public` | Local development | Seeded data — 11 problems, 17 tags, 22 examples, 0 test cases. |
| `problem_service_test` | Automated tests | Truncated and re-seeded with fixtures around every test. |

The test schema exists so the suite can truncate tables freely without touching development data. The test helper derives its connection string from the developer's own `DATABASE_URL` by rewriting the schema parameter, and refuses to run if that rewrite does not take effect — so the suite cannot fall back onto `public`. See the [README](README.md#test-database-isolation).
