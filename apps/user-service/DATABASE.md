# Database Overview

The User Service uses **PostgreSQL** as its database and **Prisma** as its ORM.

PostgreSQL was chosen because the data this service owns is inherently relational: every `Session`, `VerificationToken`, and `PasswordResetToken` row belongs to exactly one `User`, several operations (registration, email verification, password reset) must update more than one table atomically, and the service relies on real foreign key constraints and unique constraints (on `email` and `username`) to enforce data integrity at the database level rather than only in application code.

Prisma was chosen as the access layer on top of it because it provides a single schema file that is simultaneously the source of truth for the database structure (via migrations) and for a type-safe query client (`@prisma/client`) used throughout the codebase's repository layer. This keeps the shape of the data, the generated client, and the SQL migration history in sync from one definition.

---

# Entity Relationship Overview

The schema has four tables, all descending from `User`:

```
User
 ├──< Session
 ├──< VerificationToken
 └──< PasswordResetToken
```

- **User → Session** — one-to-many. A user can have any number of active sessions (one per login, registration, or Google sign-in). Each `Session` row belongs to exactly one `User` via `Session.userId`.
- **User → VerificationToken** — one-to-many. A user can have verification token rows created for them (at registration, and again each time `/auth/resend-verification` is called). In practice the service keeps at most one *unexpired, unused* token per user at a time, deleting previous ones before issuing a new one, but the relationship itself does not enforce that — it is a one-to-many foreign key, not a one-to-one.
- **User → PasswordResetToken** — one-to-many, with the same "at most one live token in practice" pattern as verification tokens.

**Cascade deletes.** All three relationships are declared with `onDelete: Cascade` (and `onUpdate: Cascade`). If a `User` row is ever deleted, PostgreSQL automatically deletes every `Session`, `VerificationToken`, and `PasswordResetToken` row that references it. The application does not need to (and does not) manually clean up child rows before deleting a user — the database guarantees there can never be an orphaned session or token row.

**Indexes.** Each child table (`sessions`, `verification_tokens`, `password_reset_tokens`) has a non-unique index on `userId`. This is what makes "find all sessions/tokens for this user" — the basis of session listing, logout-all, and the delete-previous-tokens-before-issuing-a-new-one pattern — an indexed lookup rather than a full table scan.

**Unique constraints.** Only the `User` table has application-level unique constraints: `email` and `username` are each unique. No child table has a unique constraint on `userId` — a user is expected to have many session and token rows over time, not one.

# User Table

Maps to the `users` table.

| Column | Purpose | Type | Nullable | Default | Constraints |
|---|---|---|---|---|---|
| `id` | Primary key; the user's stable identifier, referenced by every other table. | `String` (`text`) | No | Generated by Prisma as a random UUID (v4) before the row is inserted — this is a client-side default, not a PostgreSQL function. | Primary key. |
| `username` | Public, human-chosen handle. Used for public profile lookups (`GET /users/:username`) and, at registration, for uniqueness checks. | `String` (`text`) | No | None | Unique. |
| `email` | The user's email address; the account's primary identity. Also the field Google OAuth matches against to avoid duplicate accounts. | `String` (`text`) | No | None | Unique. |
| `passwordHash` | The bcrypt hash of the user's password. | `String?` (`text`) | Yes | None | Nullable specifically so that accounts created via Google OAuth (which have no password) can exist without one. |
| `firstName` | Given name. | `String` (`text`) | No | None | None |
| `lastName` | Family name. | `String` (`text`) | No | None | None |
| `avatar` | URL of the user's profile picture (set manually via `PATCH /users/me`, or automatically from the Google profile photo on Google sign-up). | `String?` (`text`) | Yes | None | None |
| `bio` | Free-text profile biography. | `String?` (`text`) | Yes | None | None |
| `country` | Free-text country field. | `String?` (`text`) | Yes | None | None |
| `college` | Free-text college/institution field. | `String?` (`text`) | Yes | None | None |
| `githubUrl` | Link to the user's GitHub profile. | `String?` (`text`) | Yes | None | None |
| `linkedinUrl` | Link to the user's LinkedIn profile. | `String?` (`text`) | Yes | None | None |
| `portfolioUrl` | Link to the user's personal portfolio site. | `String?` (`text`) | Yes | None | None |
| `role` | Authorization role, carried into the `role` claim of every issued JWT. | `Role` enum (`USER` \| `ADMIN`) | No | `USER` | Enforced to one of the two enum values by PostgreSQL. |
| `isEmailVerified` | Whether the user's email has been confirmed. | `Boolean` | No | `false` | Set to `true` either by `/auth/verify-email` or automatically for Google-created accounts (Google has already verified the email). |
| `createdAt` | Row creation timestamp. | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP`, set by PostgreSQL itself. | None |
| `updatedAt` | Last-modified timestamp. | `DateTime` (`timestamp(3)`) | No | Maintained by Prisma (`@updatedAt`) — set on every `update` issued through Prisma Client, not by a database trigger. | None |

`passwordHash` is excluded from every API response by the `sanitizeUser` / `sanitizePublicUser` utilities; it never leaves the database layer.

# Session Table

Maps to the `sessions` table.

| Column | Purpose | Type | Nullable | Default | Constraints |
|---|---|---|---|---|---|
| `id` | Primary key. Identifies a specific session so it can be targeted individually (`DELETE /sessions/:id`) and so it stays the same identity across refresh-token rotations. | `String` (`text`) | No | Client-side UUID, as with `User.id`. | Primary key. |
| `userId` | The owning user. | `String` (`text`) | No | None | Foreign key to `users.id`, `ON DELETE CASCADE ON UPDATE CASCADE`. Indexed. |
| `refreshTokenHash` | The SHA-256 hash of the session's current refresh token. | `String` (`text`) | No | None | See below. |
| `deviceName` | Reserved for a human-readable device label. | `String?` (`text`) | Yes | None | Nothing in the current implementation populates this field — it is always `null` today. |
| `browser` | Reserved for a parsed browser name. | `String?` (`text`) | Yes | None | Same as `deviceName` — always `null` in the current implementation. |
| `ipAddress` | The IP address the session was created (and most recently refreshed) from. | `String?` (`text`) | Yes | None | Populated from the request on login/registration/refresh. |
| `userAgent` | The raw `User-Agent` header of the client. | `String?` (`text`) | Yes | None | Populated from the request on login/registration/refresh. |
| `expiresAt` | When this session (and its refresh token) stops being valid. | `DateTime` (`timestamp(3)`) | No | None | Set to "now + `JWT_REFRESH_EXPIRES`" on creation, and reset to the same offset on every rotation. |
| `createdAt` | Row creation timestamp. | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP` | None |
| `updatedAt` | Last-modified timestamp — advances every time the session is rotated. | `DateTime` (`timestamp(3)`) | No | Maintained by Prisma (`@updatedAt`). | None |

**Why `refreshTokenHash` is stored instead of the token itself, and why refresh tokens are never stored in plaintext.** The refresh token is a bearer credential: whoever presents it is treated as the session's owner. If the database were ever read (via a backup, a misconfigured export, or a compromised replica), plaintext refresh tokens would let an attacker impersonate every active session immediately. Storing only a one-way hash means the database on its own is not enough to forge a session — the attacker would still need to already possess a raw token that hashes to a matching value. The hash function used is SHA-256, not bcrypt: bcrypt truncates its input at 72 bytes, and refresh tokens (JWTs) routinely exceed that length, which would make distinct tokens for the same user hash identically. SHA-256 has no such truncation and, since the token itself is already high-entropy and random rather than a low-entropy human-chosen secret, a fast deterministic hash is the appropriate tool here rather than a slow adaptive one.

**Why sessions are a separate table rather than fields on `User`.** A user can be logged in from more than one device or browser at the same time, each with its own refresh token, expiry, and metadata. Modeling that as a one-to-many table (rather than, say, a single "current refresh token" column on `User`) is what makes multiple concurrent logins, per-device logout, and "list my active sessions" possible at all. It also keeps session churn — every login and every token rotation writes a session row — isolated from the `User` row itself, which changes far less often.

# VerificationToken Table

Maps to the `verification_tokens` table.

| Column | Type | Nullable | Default |
|---|---|---|---|
| `id` | `String` (`text`) | No | Client-side UUID. |
| `userId` | `String` (`text`) | No | Foreign key to `users.id`, `ON DELETE CASCADE`. Indexed. |
| `tokenHash` | `String` (`text`) | No | None |
| `expiresAt` | `DateTime` (`timestamp(3)`) | No | None |
| `createdAt` | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP` |

**Purpose.** Backs the email verification flow. A row is created when a raw verification token is issued (at registration, and again by `/auth/resend-verification`), and is consulted by `/auth/verify-email` to confirm a submitted token is genuine and unexpired before marking the owning user's email as verified.

**Expiration.** Each token is valid for 24 hours from creation (`VERIFICATION_TOKEN_TTL_MS` in `auth.service.js`). `/auth/verify-email` checks `expiresAt` against the current time; an expired token is rejected and its row is deleted on the spot, so it cannot later be "found" by a fixed retention job — expiry is enforced at read time.

**Hashing strategy.** The column is named `tokenHash`, not `token`: only the SHA-256 hash of the raw token is ever written. The raw token exists only transiently in memory on the server that issues it (to hand to the email service) and in the link sent to the user; the database never holds a value that alone can be used to verify an email.

**Deletion strategy.** A token row is deleted the moment it is consumed by a successful verification, and also whenever it is found to be expired. `/auth/resend-verification` additionally deletes every existing verification token for the user before creating a new one, so at most one verification token is ever usable at a time.

**Security considerations.** Because the row is deleted on successful use, a verification token is single-use — resubmitting the same token after it has already verified the email returns the same generic "invalid or expired" response used for a token that never existed. That same generic message is also used for an expired token, so a caller cannot distinguish "wrong token" from "expired token" from the response alone.

# PasswordResetToken Table

Maps to the `password_reset_tokens` table.

| Column | Type | Nullable | Default |
|---|---|---|---|
| `id` | `String` (`text`) | No | Client-side UUID. |
| `userId` | `String` (`text`) | No | Foreign key to `users.id`, `ON DELETE CASCADE`. Indexed. |
| `tokenHash` | `String` (`text`) | No | None |
| `expiresAt` | `DateTime` (`timestamp(3)`) | No | None |
| `createdAt` | `DateTime` (`timestamp(3)`) | No | `CURRENT_TIMESTAMP` |

**Purpose.** Backs the forgot-password / reset-password flow. `/auth/forgot-password` creates a row (only if the submitted email matches a real account) and passes the raw token to the email service; `/auth/reset-password` consumes it to authorize changing that user's password.

**Expiration.** Each token is valid for 1 hour from creation (`PASSWORD_RESET_TOKEN_TTL_MS` in `auth.service.js`) — deliberately shorter-lived than a verification token, reflecting that a reset token grants control over the account rather than just confirming an email address. As with verification tokens, expiry is enforced when the token is looked up, and an expired row is deleted at that point.

**Hashing strategy.** Identical approach to `VerificationToken`: the column stores only the SHA-256 hash of the raw token, never the token itself.

**Deletion after use.** Successfully resetting a password deletes the token row in the same database transaction that updates the password and revokes all sessions (see [Prisma Design](#prisma-design) below), so a reset token cannot be replayed. `/auth/forgot-password` also deletes any previous reset tokens for the user before issuing a new one.

**Security considerations.** `/auth/forgot-password` returns an identical response regardless of whether the email exists, so this table's row count for a given user is never observable from the API response. A successful password reset also deletes every `Session` row for the user — not just the reset token — so a session hijacked before the reset does not survive it.

# Prisma Design

**Why Prisma Client.** The application never writes raw SQL. Every query is expressed through the generated, type-safe Prisma Client, which is derived directly from `schema.prisma`. This means the shape of a `User` or `Session` object in application code is guaranteed to match the actual database schema at build time, and query construction (filtering, includes, transactions) is done through a typed API rather than string-built SQL.

**Why migrations.** `prisma/migrations/` holds an ordered, version-controlled history of every schema change (for example, the migration that renamed `VerificationToken.token` / `PasswordResetToken.token` to `tokenHash`). This gives the schema a reproducible history: any environment can be brought to the current schema by replaying the same migrations that were used everywhere else, rather than relying on a hand-applied or inferred schema state.

**Why transactions.** Several flows in this service must make more than one write appear atomic — registration creates a `User`, a `VerificationToken`, and a `Session` together; email verification updates `User.isEmailVerified` and deletes the `VerificationToken` together; password reset updates the password, deletes every `Session`, and deletes the `PasswordResetToken` together. `prisma.$transaction(...)` is used in each of these cases so that a failure partway through leaves no partial state — for example, a user is never left created without a verification token, and a password is never changed without also revoking existing sessions.

**Why the repository pattern wraps Prisma.** Every table has a corresponding repository module (`user.repository.js`, `session.repository.js`, `verificationToken.repository.js`, `passwordResetToken.repository.js`) that is the only code allowed to call `prisma.<model>.*` directly. Each repository function optionally accepts a Prisma client argument (defaulting to the shared client), which is how a single logical operation spanning several repositories can be run inside one `$transaction` — the transaction's scoped client is simply passed through instead of the default one. This keeps all Prisma-specific query construction in one layer, and keeps the service layer (business logic) and controller layer (HTTP handling) free of direct database access.

# Indexes

| Table | Index | Type | Reason |
|---|---|---|---|
| `users` | `users_pkey` on `id` | Primary key (btree) | Row lookup by id — used by every authenticated request to load `req.user`'s underlying account. |
| `users` | `users_email_key` on `email` | Unique (btree) | Enforces email uniqueness and makes login, registration's uniqueness check, and forgot-password's lookup-by-email efficient. |
| `users` | `users_username_key` on `username` | Unique (btree) | Enforces username uniqueness and makes registration's uniqueness check and public-profile lookup (`GET /users/:username`) efficient. |
| `sessions` | `sessions_pkey` on `id` | Primary key (btree) | Row lookup by id — used by session deletion. |
| `sessions` | `sessions_userId_idx` on `userId` | Non-unique (btree) | Makes "all sessions for this user" (session listing, logout-all, delete-all-except-current) an indexed lookup instead of a table scan. |
| `verification_tokens` | `verification_tokens_pkey` on `id` | Primary key (btree) | Row lookup by id. |
| `verification_tokens` | `verification_tokens_userId_idx` on `userId` | Non-unique (btree) | Makes "delete this user's previous verification tokens" (done before issuing a new one) an indexed lookup. |
| `password_reset_tokens` | `password_reset_tokens_pkey` on `id` | Primary key (btree) | Row lookup by id. |
| `password_reset_tokens` | `password_reset_tokens_userId_idx` on `userId` | Non-unique (btree) | Makes "delete this user's previous reset tokens" an indexed lookup. |

Note that `tokenHash` and `refreshTokenHash` are **not** indexed. Lookups by these hashes (`findByHash`, `findByUserIdAndHash`) are always additionally scoped by `userId` where that's available, or are infrequent, session/token-verification-time operations rather than hot-path queries — the schema does not currently add a dedicated index on the hash columns themselves.

# Constraints

**Unique constraints**

- `users.email` — a given email address can belong to at most one account. This is also what Google OAuth relies on to avoid ever creating a duplicate account for an email that already has a password-based account, or vice versa.
- `users.username` — a given username can belong to at most one account.

**Foreign keys**

- `sessions.userId → users.id`
- `verification_tokens.userId → users.id`
- `password_reset_tokens.userId → users.id`

All three are declared `ON DELETE CASCADE ON UPDATE CASCADE`.

**Cascade delete behavior.** Deleting a `User` row automatically deletes every `Session`, `VerificationToken`, and `PasswordResetToken` row referencing it, enforced by PostgreSQL itself rather than by application code issuing separate delete statements. This guarantees referential integrity even if a user were deleted through a path that doesn't go through the service's own repositories (a direct database operation, for instance) — there is no way to end up with a session or token row that references a nonexistent user.

# Security Decisions

- **Passwords → bcrypt.** User passwords are hashed with bcrypt (cost factor 12) before storage. Bcrypt's deliberate slowness is appropriate here because passwords are relatively low-entropy, human-chosen secrets that benefit from an adaptive, intentionally expensive hash to resist brute-forcing.
- **Verification tokens → SHA-256.** Stored as `VerificationToken.tokenHash`. Unlike passwords, these tokens are high-entropy, randomly generated values, so a fast cryptographic hash is both sufficient and appropriate — and necessary in practice, since bcrypt's 72-byte input truncation would cause distinct long tokens to collide.
- **Reset tokens → SHA-256.** Stored as `PasswordResetToken.tokenHash`, for the same reasons as verification tokens.
- **Refresh tokens → hashed.** Stored as `Session.refreshTokenHash`, also with SHA-256, for the same reasons. This is what makes refresh token rotation meaningful: a session is matched by comparing the hash of the presented token against the stored hash, so a previous (rotated-out) refresh token no longer matches anything.
- **Email uniqueness.** Enforced by a database-level unique constraint on `users.email`, not just an application-level check, so it holds even under concurrent registration attempts for the same address.
- **Username uniqueness.** Enforced the same way, by a database-level unique constraint on `users.username`.
- **Session invalidation.** Sessions are deleted (not just marked inactive) when they are no longer valid: a single session on logout, every session on logout-all, every session on password reset, and an individual expired session the moment it's encountered during a refresh attempt. There is no "soft delete" or status flag on `Session` — a row's existence *is* the record of whether that session is still active.

# Future Expansion

The schema is scoped entirely to identity and account data — it has no columns or tables describing problems, submissions, or judging results — so other CodeArena services can be added without requiring any change to this schema:

- **Problem Service** and **Judge Service** would reference users by `User.id` (a stable UUID) from their own databases, the same way this service's own `Session`, `VerificationToken`, and `PasswordResetToken` tables do, without needing a foreign key into this database or any schema change here.
- **Gateway** can authorize requests using the `role` claim already embedded in the JWTs this service issues, without querying this database directly.
- Because `role` is a real enum (`USER` | `ADMIN`) rather than a free-text field, future authorization logic in other services has a fixed, well-defined set of values to check against without needing to coordinate a schema migration in this service.

Nothing about the current design assumes a single-service deployment — the `User` table is intentionally the full extent of what this service needs to own.
